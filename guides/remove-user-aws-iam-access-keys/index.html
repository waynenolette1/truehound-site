How to remove an IAM user and deactivate their access keys

Sources checked 21 October 2026. 5 minute read.

The short answer

Download the IAM credential report to see each user's keys and when they were last used. Deactivate the leaver's access keys first, because that is reversible if something breaks. Then delete the password, keys, certificates, SSH keys, service-specific credentials and MFA, remove policies and group memberships, and only then delete the user. Once deleted, the user and its keys cannot be recovered.

On this page

  2. Deactivate first, because it can be undone

Find the user and their keys in the credential report

In the IAM console choose Credential report, then Download Report. From the CLI run aws iam generate-credential-report and then aws iam get-credential-report. IAM makes a new report at most once every four hours.

The report is a CSV. The columns that matter for offboarding are user, password_last_used, mfa_active, access_key_1_active, access_key_1_last_used_date, and the same pair for access key 2.

The report does not show service-specific credentials (such as CodeCommit passwords or Bedrock API keys) or any keys beyond the first two. Use ListServiceSpecificCredentials and ListAccessKeys for the full picture.[2]

Before removing a user, AWS suggests checking their recent service activity. An IAM user named after a person is sometimes what a production job uses.

Deactivate first, because it can be undone

  1. Step 1. Deactivate the access keys[3]

    Open the user, go to the Security credentials tab, and in Access keys choose Actions, then Deactivate. From the CLI use aws iam update-access-key with the status set to Inactive.

    A deactivated key can no longer be used by API calls, and you can activate it again if needed. That makes it a safe first move when you are not sure what uses the key.

  2. Step 2. Block the user without deleting anything[1]

    To stop all access while keeping credentials in place, attach a policy that denies every action on every resource. Remove the policy to restore access.

  3. Step 3. Watch the last-used date[3]

    Check the Access key last used column, or run aws iam get-access-key-last-used. If nothing breaks after a few days, delete.

Delete the IAM user in the order AWS requires

In the console, deleting a user also removes their group memberships, password, inline policies, attached managed policies (the policies themselves are kept) and MFA device. The console asks you to deactivate active access keys first.

With the CLI or API you must remove each attached item yourself before DeleteUser will succeed. AWS documents this order:

  1. Step 1. Delete the console password[1]

    aws iam delete-login-profile

  2. Step 2. Delete the access keys[1]

    aws iam list-access-keys, then aws iam delete-access-key for each one.

  3. Step 3. Delete signing certificates and SSH public keys[1]

    aws iam list-signing-certificates and delete-signing-certificate, then list-ssh-public-keys and delete-ssh-public-key. A deleted credential is gone for good.

  4. Step 4. Delete service-specific credentials[1]

    aws iam list-service-specific-credentials, then delete-service-specific-credential. These include Git credentials for CodeCommit.

  5. Step 5. Deactivate and delete MFA devices[1]

    aws iam list-mfa-devices, then deactivate-mfa-device. For a virtual device, also run delete-virtual-mfa-device.

  6. Step 6. Remove policies and group memberships[1]

    Delete inline policies (list-user-policies, delete-user-policy). Detach managed policies (list-attached-user-policies, detach-user-policy). Remove the user from every group (list-groups-for-user, remove-user-from-group).

  7. Step 7. Delete the user[1]

    aws iam delete-user. This cannot be undone.

IAM Identity Center users are different

If people sign in through IAM Identity Center, they are not IAM users, and you offboard them in Identity Center instead. Disabling them is not instant: someone with an open access portal session can keep assuming roles until you remove their assignments, and role sessions can last up to 12 hours.

  1. Step 1. Deny first[6],[7]

    Add the user's ID to a deny-all policy, either in the permission set's inline policy or in a service control policy, using the identitystore:UserId condition key.

  2. Step 2. Remove assignments and disable in your IdP[6]

    Remove the user from all groups and permission set assignments. If you use an external IdP or Active Directory, disable the user there.

  3. Step 3. Delete sessions, then disable[6]

    In the Identity Center console open the user, go to Active sessions, and delete them. Only then choose Disable user access. If you disable first, you can no longer end the session from the console. Keep the deny policy for at least 12 hours.

Root and shared credentials

AWS says root credentials should be shared only with people who have a strict business need, root should have MFA, and root should not have access keys. If the leaver knew the root password or held a root MFA device, change the password and replace that MFA device.

AWS also recommends a group email address for the root user, so account notices do not go to one person's inbox after they leave.

Rotate any long-term access keys the leaver could have copied, such as keys for a shared deploy user. AWS lets a user hold two keys at once so you can switch to a new key before deleting the old one.[5],[4],[2]

Questions

Should I deactivate or delete an IAM access key?
Deactivate first. A deactivated key stops working but can be turned back on. Delete it once you are sure nothing depends on it, because deletion is permanent.
Why does aws iam delete-user fail?
With the CLI or API, the user must have no password, access keys, certificates, SSH keys, service-specific credentials, MFA devices, inline or attached policies, or group memberships left. Remove each one, then retry.
Can I restore a deleted IAM user?
No. AWS states that once an IAM user and its access keys are deleted, they cannot be restored or recovered.
Does the credential report show every credential?
No. It covers passwords, the first two access keys, MFA devices and signing certificates. Service-specific credentials and extra keys need ListServiceSpecificCredentials and ListAccessKeys.
Is disabling an IAM Identity Center user immediate?
Not for open role sessions, which can run up to 12 hours. Add a deny policy, remove assignments, delete active sessions, then disable the user.
