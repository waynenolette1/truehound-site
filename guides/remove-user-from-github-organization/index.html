How to remove a user from a GitHub organization

Sources checked 21 October 2026. 5 minute read.

The short answer

Go to your organization's People tab, select the person and choose Remove from organization. Outside collaborators are removed separately, from the Outside collaborators list, and pending invitations must be cancelled too. Removing someone does not revoke deploy keys or secrets they could see, so rotate those afterwards. GitHub keeps a removed member's data for three months in case you reinstate them.

Members, outside collaborators and pending invitations

GitHub tracks three kinds of people, and each one is removed in a different place.

  • Members belong to the organization and get access through teams and base permissions.
  • Outside collaborators are not members. They are added to individual repositories. Removing them from the organization's list removes them from every repository.
  • Pending invitations are people who were invited but never accepted. They are not members yet, but an open invite can still be accepted, so cancel it.[1],[5],[4]

Remove a person in organization settings

  1. Step 1. Remove a member[1]

    Open your profile menu, go to Organizations, and pick your organization. Open the People tab, tick the members to remove, and from the members selected dropdown choose Remove from organization. Review the list and confirm with Remove members.

  2. Step 2. Remove an outside collaborator from all repositories[3]

    On the People tab, open Outside collaborators in the sidebar. Tick the people to remove, open the dropdown above the list, and choose to remove them from all repositories. Review and confirm.

  3. Step 3. Check seats if you pay per license[1]

    Under volume license billing, GitHub does not lower your paid license count when you remove someone. Downgrade the seat count yourself if you want to pay for fewer.

Remove a person with the REST API

Scripts help when you offboard several people at once or across several organizations. The authenticated user must be an organization owner.

  • DELETE /orgs/{org}/members/{username} removes a member. It also removes them from all teams, and they lose access to the organization's repositories. A successful call returns 204.
  • DELETE /orgs/{org}/memberships/{username} removes an active member, or cancels the invitation if the person was only invited. The user gets an email either way.
  • DELETE /orgs/{org}/invitations/{invitation_id} cancels one pending invitation.
  • GET /orgs/{org}/outside_collaborators lists outside collaborators. DELETE /orgs/{org}/outside_collaborators/{username} removes one from every repository. It returns 422 if the person is actually a member, so use the members endpoint for them.
  • Membership that comes from an enterprise team is not removed by these calls. Remove the person from that enterprise team as well.[4],[5]

What happens to forks, invites and reinstatement

  • Removed members lose access to their private forks of your private repositories. Local clones on their laptop stay with them; they just cannot sync.
  • For outside collaborators, GitHub deletes their forks of private repositories when you remove them. Again, local clones remain.
  • Invitations the removed member sent and that were never accepted are cancelled.
  • GitHub saves a removed member's data for three months. Invite them back in that window and you can restore their role, team memberships, repository access, private forks, issue assignments and stars.[1],[3],[2]

Revoke what removal does not touch

  1. Step 1. Rotate deploy keys[7]

    A deploy key belongs to a repository, not a person. GitHub says the key stays active after the user who added it is removed. Deploy keys never expire, are usually not protected by a passphrase, and a write key can do what an organization admin can. Delete any key the leaver created or held a copy of, and add a new one.

  2. Step 2. Rotate Actions secrets they could read[8]

    GitHub warns that anyone with write access to a repository has read access to all secrets configured in it. If the leaver had write access, assume they could have seen those values. Rotate the secrets in the repositories they could write to, starting with cloud and payment keys.

  3. Step 3. Revoke SAML SSO credential authorizations[6]

    If your organization uses SAML single sign-on on GitHub Enterprise Cloud, open People, select the member, and open SAML identity linked. Under Authorized credentials, revoke each personal access token and SSH key.

    Revoking only removes the SAML authorization. The token or key itself still exists on their account; it simply can no longer reach your organization.

Removing a person from the organization is not the same as making their old credentials useless. Deploy keys and secrets are shared, so they need rotating even after a clean removal.

Enterprise Managed Users and SCIM

With Enterprise Managed Users, your identity provider owns the account. Usernames, profile data, organization membership and repository access are controlled from the IdP, which provisions accounts with SCIM.

So offboard in the IdP, not on GitHub. If you use SCIM, remove the person from the GitHub application in your IdP and from any linked IdP groups. For managed users whose membership comes from IdP groups, remove them from every group linked to a team with access to the organization.[9],[1]

Questions

Does removing someone from a GitHub organization delete their account?
No. It removes their access to your organization. Their personal GitHub account stays. Only Enterprise Managed Users accounts are controlled by your identity provider.
Can I undo removing a member?
Yes, within three months. Invite them back and GitHub can restore their role, teams, repository access and private forks.
Do they keep copies of private code?
Any local clone they made stays on their machine. GitHub removes their access to private forks of your private repositories, and deletes those forks for outside collaborators.
Do deploy keys stop working when the person who added them leaves?
No. Deploy keys belong to the repository, not the person, and they do not expire. Delete and replace them yourself.
Why does the outside collaborator API return 422?
The person is a member, not an outside collaborator. Use DELETE /orgs/{org}/members/{username} instead.
