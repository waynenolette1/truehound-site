How to rotate GitHub deploy keys when someone leaves

Sources checked 22 October 2026. 6 minute read.

The short answer

A deploy key belongs to a repository, not a person, so it keeps working after the person who added it leaves. To rotate one, generate a new key pair, add the new public key to the repository, switch the server or service to the new private key, then delete the old key. Deploy keys cannot be edited, only replaced. Do the same for Actions secrets the leaver could read, and revoke their fine-grained personal access tokens' access to your organization.

Why deploy keys survive offboarding

  • A deploy key is an SSH key attached to one repository. The private half lives on a server, a CI system, or someone's laptop.
  • GitHub says the key stays active if the user who created it is removed, and that deploy keys are not linked to organization membership.
  • Deploy keys have no expiry date and are usually not protected by a passphrase.
  • Keys are read-only by default, but a key with write access can do what an organization admin or a personal repository collaborator can do.[1]

If the leaver ever had a copy of a deploy key's private half, removing their GitHub account changes nothing for that key. Treat it as theirs until you replace it.

List the deploy keys in each repository

  1. Step 1. In repository settings[1]

    Open the repository, go to Settings, then Deploy keys, to see the keys attached to that repository.

  2. Step 2. With the REST API or GitHub CLI[2],[3]

    GET /repos/{owner}/{repo}/keys lists a repository's deploy keys. There is one list per repository, so loop over your repositories. With the GitHub CLI: gh api --paginate repos/YOUR-ORG/REPO/keys. Note the keys with read_only set to false first; those can push.

  3. Step 3. Decide which keys the leaver could have held

    Keys the leaver created, keys on servers they could log in to, and keys nobody can explain all go on the rotate list. If you cannot say where a private key lives, rotate it.

Rotate a deploy key without breaking deploys

  1. Step 1. Generate a new key pair where it will be used[1]

    Run ssh-keygen on the server or in the service that needs access. Each repository needs its own key; GitHub does not let you reuse a deploy key across repositories.

  2. Step 2. Add the new public key[1],[2]

    In the repository, open Settings, then Deploy keys, then Add deploy key. Paste the public key and only tick Allow write access if the system really pushes. By API, POST /repos/{owner}/{repo}/keys with read_only set to true creates a read-only key.

  3. Step 3. Switch the system over and test it

    Point the server or pipeline at the new private key and run a fetch or a deploy to confirm it works.

  4. Step 4. Delete the old key[2]

    Remove the old key in Deploy keys, or call DELETE /repos/{owner}/{repo}/keys/{key_id}. GitHub's API reference says deploy keys are immutable: to change one, remove it and create a new one.

Rotate the Actions secrets they could read

GitHub warns that anyone with write access to a repository has read access to all secrets configured in it. If the leaver could write to a repository, assume they could see its secrets, and rotate the value at the source first (the cloud key, the API token), then update the secret.

Organization secrets are shared with all repositories, private repositories, or a selected list. Check each one's repository access in organization Settings, then Secrets and variables, then Actions; if any of those repositories was writable by the leaver, rotate it. The list endpoints such as GET /orgs/{org}/actions/secrets show names and dates, never values. To store the new value, use the Update button there or gh secret set --org YOUR-ORG NAME.

Where a cloud provider supports it, GitHub suggests OpenID Connect so workflows stop storing long-lived cloud credentials as secrets at all.[4],[5],[6]

Revoke personal access tokens and SSO authorizations

  • Organization owners can see every fine-grained personal access token that can reach the organization under Settings, then Personal access tokens, then Active tokens, filter by owner, and revoke them. The person gets an email.
  • That page covers fine-grained tokens only. Classic tokens keep working against your organization until they expire, unless your token policy restricts classic tokens.
  • In Personal access tokens, then Settings, owners can require approval for fine-grained tokens, set a maximum lifetime, and restrict classic tokens.
  • If you use SAML single sign-on, the member's SAML identity page lists authorized credentials, and you can revoke each token and SSH key there. The full removal steps are in /guides/remove-user-from-github-organization.[7],[8],[9]

Optional: move people to SSH certificates

On GitHub Enterprise Cloud, an organization can trust an SSH certificate authority and sign short-lived certificates for members and outside collaborators. Certificates from CAs added after 27 March 2024 must have a lifetime under one year, and they expire on their own. Single certificates cannot be revoked; removing the CA invalidates everything it signed. That makes certificates a good fit for people, while machines are better served by GitHub Apps, whose installation tokens expire after one hour.[10],[1]

Questions

Do deploy keys expire?
No. GitHub describes deploy keys as credentials that do not have an expiry date. Replace them yourself.
Can I edit a deploy key to make it read-only?
No. Deploy keys are immutable. Add a new read-only key, switch over, and delete the old one.
Does removing a person revoke their personal access tokens?
Removing them from the organization ends their member access, but owners should still review Active tokens for fine-grained tokens, and SAML authorizations where SSO is on.
Which secrets should I rotate first?
Secrets in repositories the leaver could write to, and organization secrets shared with those repositories. Start with cloud, payment and production database credentials.
Is there a replacement for deploy keys?
GitHub recommends GitHub Apps for stronger security: their installation tokens are scoped to chosen repositories and expire after one hour.
