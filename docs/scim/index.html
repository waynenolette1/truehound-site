SCIM

Last compared with the product's code 25 October 2026.

SCIM is used in four different ways in Truehound. They are separate features, and you can use any one without the others.

What you need, and what is not on yet

SCIM needs a team workspace. Truehound's SCIM client covers a fixed set of apps (listed below), not every SCIM app, and the SCIM bridge is self-serve, not a managed service. Both take effect only with the apps' own plans that allow SCIM.

On this page

  1. 1. Your identity provider provisions people into Truehound
  2. 2. Truehound provisions and deactivates people in apps
  3. 3. Truehound reads an app through its SCIM endpoint
  4. 4. The SCIM bridge: SCIM for an app that has none
  5. SSO into Truehound is separate

1. Your identity provider provisions people into Truehound

Truehound is a SCIM 2.0 server (RFC 7643 and 7644). Okta, Microsoft Entra ID, JumpCloud or OneLogin push users to it, with the base path /api/scim/v2 on your API address and a bearer token that Setup shows once.

The provider's pushes drive the lifecycle. A new user runs your joiner steps, a new department or title runs the mover steps, and a deactivation puts the person on the Left, still has access board and opens their offboarding for approval. Users are created, replaced, patched and deleted, and groups are supported.

Pushed groups map to Truehound roles for Okta (Push Groups) and Entra (group assignment). A user gets the highest role mapped to one of their groups, otherwise the roles attribute, otherwise member. An owner is never changed. Every write is sealed in Proof.

2. Truehound provisions and deactivates people in apps

Over SCIM, Truehound can create a user with a role or group, change the role, and deactivate the user, then read the app again to prove each change. The apps with SCIM provisioning built in are Figma, Slack, Atlassian, Notion and Zoom, and Miro, monday.com and Canva for removal.

Slack needs a plan that includes SCIM. Provisioning and removal run under your approval policy.

3. Truehound reads an app through its SCIM endpoint

For apps that expose SCIM on a plan that includes it, you paste the SCIM bearer token on the app's card. Truehound reads the user list and can deactivate users. Each app is tested against its documented responses. The integrations directory marks which apps connect this way.

4. The SCIM bridge: SCIM for an app that has none

On the SCIM bridge page an admin makes a SCIM 2.0 endpoint for an app that has no SCIM. Behind it is the app's API, through a custom connector, or a browser playbook. It has its own bearer token, shown once, and its path is /api/scim-bridge/<id>/v2 on your API address.

Your identity provider then deprovisions people in that app like in any SCIM app. A deactivation uses the app's own call, then Truehound reads the app again. The identity provider gets success only when that read agrees.

Okta's PATCH, Entra's string booleans and DELETE all deactivate. Creating a user works only when you set a create call on a custom connector. Attribute changes other than deactivation, and groups, are not written to the app. Every call is listed and sealed in Proof without a body or credential.

SSO into Truehound is separate

Signing people in to Truehound uses SAML 2.0 or OIDC per workspace, on email domains you prove you own, and is set up under Developers. See API and webhooks.
