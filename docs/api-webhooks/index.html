API and webhooks

Last compared with the product's code 25 October 2026.

Everything the app shows about people, accounts, findings, reviews, offboardings, evidence and Proof is available over a REST API, and so are the actions: requesting and approving access, launching and deciding reviews, and starting offboardings. Webhooks tell your systems when something changes.

What you need, and what is not on yet

The API, webhooks and SIEM streaming need a team workspace. The address to call is shown on your workspace's Developers page, because the api.truehound.io name is not live yet. The OpenAPI 3.1 file is served at /api/v1/openapi.json on that address, and the Developers page renders every operation from it.

Make an API key

  1. Step 1. Open Developers in your workspace

    Choose the scopes the key needs, such as people:read or config:write.

  2. Step 2. Copy the key once

    A key belongs to one workspace. Truehound stores only its hash, so the key is shown a single time. It has the form th_ followed by an id and a secret.

  3. Step 3. Call the API

    Send the key as a Bearer token. A key without the scope an operation needs is refused with 403.

Basics

  • Lists answer { data, next_cursor }. Pass next_cursor back as cursor to get the next page.
  • Errors answer { ok: false, error, message }, with the field or scope named in plain words.
  • The limit is 600 requests a minute per key.
  • Data is what your workspace last published from each app, so it matches what your team sees.
  • The API covers people, accounts, systems, findings, leavers, reviews (launch, assign, decide, sign off), offboardings, lifecycle runs, access requests (create, approve, deny, cancel, remind, revoke), evidence, access-path queries, Proof events and verification, review schedules, role bundles, custom roles, the approval policy, separation-of-duties rules, webhooks and SIEM destinations.
  • The whole reference, with request and response fields and a curl line for each operation, is on the Developers page.

Webhooks

Truehound posts an event to your https endpoint when something changes, once per change. You make an endpoint in Developers or with the API, and its signing secret is shown once. You can rotate it, send a test event, read the delivery log, and send any delivery again.

Events: leaver.detected, review.launched, review.signed, review.ended, revoke.verified, revoke.failed, offboarding.started, offboarding.completed, finding.created, finding.resolved, source.connected, proof.sealed, access.requested, access.approved, access.denied, access.granted, access.revoked, lifecycle.run_planned, lifecycle.run_completed, person.changed and ping.

Check the signature

Every request carries a Truehound-Signature header of the form t=unix-seconds,v1=signature, where the signature is the HMAC-SHA256 of the text t, a dot, and the raw body, keyed with your endpoint secret. Check it against the raw body before you parse it, and reject requests whose timestamp is more than five minutes old.

Answer with any 2xx status within 10 seconds. Anything else is retried after 1 minute, 5 minutes, 30 minutes, 2 hours, 8 hours and 24 hours, and every attempt is in the delivery log.

Stream Proof to your SIEM

Proof can be streamed as OCSF to an S3 bucket, Splunk HEC, Datadog or a signed webhook, set up as SIEM destinations in Developers or over the API. Each destination has a test and a delivery log. The export of every admin action is also available as a file.

Also for developers

  • Manage schedules, the approval policy, role bundles and webhooks as code with the Terraform provider.
  • Let Claude and other assistants work with your workspace through the MCP server.
  • Sign people in to Truehound with SAML 2.0 or OIDC on email domains you prove you own, with roles from your IdP groups, and provision them with SCIM.
  • Add an app Truehound does not have with the no-code custom connector described in Connect your apps.
